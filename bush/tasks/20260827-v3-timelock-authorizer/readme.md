# 2026-08-27 - V3 Timelock Authorizer

Deployment of the `TimelockAuthorizer`, meant to replace the `BootstrapAuthorizer` the Vault is deployed with.

This Authorizer implementation allows defining a delay per action identifier. Users can only execute functions directly when there is no delay. Otherwise, they're granted permission to schedule an action, which can then be executed by the Authorizer after the delay. It also introduces Granters and Revokers, to allow controlled delegation of permission handling to third parties, which eases the burden on governance and allows the system to scale.

This task only deploys the Authorizer: there is no `TimelockAuthorizerMigrator`, so `Root` is set directly in the constructor and all configuration happens afterwards, as described below. The `TimelockExecutionHelper` is deployed by the `TimelockAuthorizer` constructor; this task looks its address up and saves and verifies it alongside the Authorizer.

## Deployment Inputs

- `Root`: the account that is root from the very first block. It's a granter, revoker and canceler for every action, and the only account that can schedule delay changes.
- `NextRoot`: set as the pending root, which can call `claimRoot` at any time, skipping the root transfer delay. This only exists to support handovers (e.g. deploy with the deployer as `Root` and governance as `NextRoot`); it is the zero address when `Root` is already the intended owner.
- `Vault`: used to compute the `setAuthorizer` action ID, which caps every other delay.
- `RootTransferDelay`: the delay for `scheduleRootChange`, i.e. transfers of root after the initial one.

## Post-Deployment Steps

The Authorizer does nothing until governance points the Vault at it, and it enforces no delays until root schedules them.

1. Hand over control: the `BootstrapAuthorizer` owner calls `VaultAdmin.setAuthorizer(address)` on the Vault with the new Authorizer's address.
2. Grant the initial permissions, with [`20260827-v3-grant-permissions`](../../scripts/20260827-v3-grant-permissions).

**No delays are currently configured**, which means every action is performed directly by whoever holds the permission, and root grants permissions immediately. The Authorizer behaves like a plain allowlist until delays are turned on.

### Turning the timelock on

The tiered set of delays that would normally be applied is kept in [`settings.ts`](./settings.ts) as `ProposedGrantDelays` / `ProposedExecuteDelays`; export those as the active `GrantDelays` / `ExecuteDelays` to adopt it, then:

1. Set the `setAuthorizer` delay first. No delay can be set longer than this one (`setDelay` reverts with `DELAY_EXCEEDS_SET_AUTHORIZER` otherwise), so it has to be configured before any other.
2. Set the remaining delays. Delay changes cannot be applied directly: root calls `scheduleDelayChange` / `scheduleGrantDelayChange` / `scheduleRevokeDelayChange`, waits `MINIMUM_CHANGE_DELAY_EXECUTION_DELAY` (5 days), and then calls `execute`. That 5-day wait is the cost of enabling a delay; it does not apply while delays are zero.

Grant every permission you already know you need *before* adding grant delays: once an action has one, handing out that permission requires `scheduleGrantPermission` plus the delay, with no way to skip it.

Action IDs come from `action-ids/<network>/action-ids.json`, generated by `npx hardhat save-action-ids --network <network>`. `build-timelock-authorizer-config` renders [`settings.ts`](./settings.ts) into `timelock-authorizer-config/<network>.json`, and `verify-timelock-authorizer-config` diffs that against the delays stored onchain.
